# 設計PRの手順
設計レビュー → 承認ゲート → `status` の更新とコミットの順に進め、PR本文の材料を集める。設計レビューの定義は `docs/workflow/design-workflow.md` の「PR作成タスク」節が正本です。

## 1. 設計メモを確認する
設計メモ `docs/design-notes/<slug>.md` が存在し、`status: draft` であることを確認する。満たさない場合は、理由をユーザーに伝えて終了する。

完了条件: 設計メモが `status: draft` で存在している

## 2. バリデータを並行して起動する
次の2つのサブエージェントを、1つのメッセージで同時に起動する。

- `design-spec-validator`: 設計メモのパスを渡す
- `coding-standards-validator`: モード「設計」と設計メモのパスを渡す

どちらかがエラー形式で返った場合は、入力を正して起動し直す。

完了条件: 両方のバリデータからレビュー結果を受け取っている

## 3. must を修正する
- 各 must 指摘の根拠(規約・spec)を自分でも確認し、設計メモを修正する
- 根拠を確認した結果、誤検知だと判断した must は修正せず、判断した理由を添えて「判断待ち」に回す
- 修正した場合は手順2の2つのバリデータを再度起動し、新しい must が出ていないことを確認する。再レビューは最大2回とし、2回目でも残った must は「未解決の must」として手順4で提示する

完了条件: 全ての must が「修正済み」「判断待ち」「未解決」のいずれかに分類されている

## 4. 承認ゲートで提示する
次の形式でレポートを提示し、作業を止めてユーザーの判断を待つ。判断待ちがなくても、設計メモの確定はユーザーが行うため必ず提示する。

```md
## 設計レビュー結果
- 設計メモ: docs/design-notes/<slug>.md
- レビュー回数: 2 回(初回 + 再レビュー1回)
- 検証: design-spec-validator(参照 spec: ...)、coding-standards-validator(検証した規約: ...)

## 修正済みの must
- [spec] 変更対象 spec に `csv-export.md` を追加した(一覧の漏れ)

## 未解決の must
なし

## 判断待ち
1. [should][コード規約] ...(architecture.md#logic)
2. [must→判断待ち][spec] ...。誤検知と判断した理由: ...

設計メモを確定する場合は「確定」、修正する場合は番号や修正内容を指示してください
```

- 各項目の先頭に出元のバリデータ(`[spec]` / `[コード規約]`)を付ける
- 判断待ちには通し番号を振り、ユーザーが番号で指示できるようにする

完了条件: レポートを提示し、ユーザーの返答を受け取っている

## 5. ユーザーの指示に対応する
- 修正の指示があれば設計メモを修正し、手順2からやり直す(手順3の再レビュー回数は数え直す)
- 「確定」と返答されたら次の手順に進む。このとき修正しなかった判断待ち・未解決の must を「見送った指摘」として記録する

完了条件: ユーザーが設計メモを確定し、見送った指摘が記録されている

## 6. status を更新してコミットする
設計メモの `status` を `approved` に更新し、レビューでの修正とあわせて1つのコミットにする。コミットメッセージにはレビューで修正した内容を要約する。

完了条件: `status: approved` の設計メモがコミットされている

## 7. PR本文の材料を集める
設計PRのテンプレートの各節に対応する材料を、次のとおり集める。

| 節 | 材料 |
|---|---|
| 概要 | 設計メモの「実装背景 Why」と「実現したい内容 What」の要約 |
| レビューしてほしい点 | 設計メモの How に書いた判断が分かれる前提、Why Not で比較した代替案のうち判断が際どいもの |
| 見送った指摘 | 手順5で記録した見送った指摘。なければ「なし」 |

完了条件: テンプレートの全ての節の材料が揃っている
