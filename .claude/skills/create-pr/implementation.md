# 実装PRの手順
実装レビュー → 承認ゲート → テスト → コミットの順に進め、PR本文の材料を集める。実装レビューの定義は `docs/workflow/implementation-workflow.md` の「PR作成タスク」節が正本です。

## 1. spec/ADR昇格が済んでいることを確認する
`git fetch` の後、`git diff --name-status $(git merge-base origin/main HEAD) -- docs/design-notes/<slug>.md` で、設計メモが削除済み(`D`)であることを確認する。削除されていない場合は、作業を止めて `/promote-spec-adr` を先に実行するよう案内する。

完了条件: spec/ADR昇格タスクで設計メモが削除済みであることを確認している

## 2. バリデータを並行して起動する
次の2つのサブエージェントを、1つのメッセージで同時に起動する。

- `coding-standards-validator`: モード「実装」、基準 `main` を渡す
- `spec-adr-validator`: 基準 `main` を渡す

どちらかがエラー形式で返った場合は、入力を正して起動し直す。

完了条件: 両方のバリデータからレビュー結果を受け取っている

## 3. must を修正する
- 各 must 指摘の根拠(規約・ソースコード)を自分でも確認し、ソースコード・spec・ADR を修正する
- 根拠を確認した結果、誤検知だと判断した must は修正せず、判断した理由を添えて「判断待ち」に回す
- 修正した場合は手順2の2つのバリデータを再度起動し、新しい must が出ていないことを確認する。ソースコードの修正で spec やコメントとの整合が崩れていないかも、この再レビューで確認できる。再レビューは最大2回とし、2回目でも残った must は「未解決の must」として手順4で提示する

完了条件: 全ての must が「修正済み」「判断待ち」「未解決」のいずれかに分類されている

## 4. 承認ゲートで提示する
判断待ち・未解決の must のどちらもない場合は、提示せずに手順6へ進む。ある場合は次の形式でレポートを提示し、作業を止めてユーザーの判断を待つ。

```md
## 実装レビュー結果
- 対象: main との差分(分岐点 <短縮コミットハッシュ>)
- レビュー回数: 2 回(初回 + 再レビュー1回)
- 検証: coding-standards-validator(検証した規約: ...)、spec-adr-validator(検証した spec: ...、検証した ADR: ...)

## 修正済みの must
- [コード規約] src/project_name/logic/score.py:12 現在時刻の取得を infrastructure 層に移した(architecture.md#logic)

## 未解決の must
なし

## 判断待ち
1. [should][コード規約] src/project_name/cli.py:30 ...(naming.md#関数名)
2. [should][spec] docs/spec/csv-export.md の「インターフェース」 ...
3. [must→判断待ち][コード規約] ...。誤検知と判断した理由: ...

修正する番号と、必要なら修正方法を指示してください(例: 「1,3 を修正。2 は対応不要」)
```

- 各項目の先頭に出元のバリデータ(`[コード規約]` / `[spec]`)を付ける
- 判断待ちには通し番号を振り、ユーザーが番号で指示できるようにする

完了条件: レポートを提示し、ユーザーの返答を受け取っている

## 5. ユーザーの判断を反映する
- 修正を指示された項目を、指示された方法で修正する
- 修正した場合は手順2の2つのバリデータを再度起動し、新しい must が出ていないことを確認する。新しい must が出た場合は手順3と同じ扱いで修正し、再レビューは手順3とは別に最大2回とする。それでも残った must や判断待ちが出た場合は、手順4の形式で再度提示する
- 修正しなかった判断待ち・未解決の must を「見送った指摘」として記録する

完了条件: 判断待ちと未解決の must の全項目について、ユーザーの判断(修正する・しない)が反映され、見送った指摘が記録されている

## 6. テストと型チェックを実行する
- `uv run pytest` と `uv run pyright` を実行する。失敗した場合は、コミットも PR作成もせずに結果をユーザーに伝えて終了する
- `pyproject.toml` がないなどの理由で実行できない場合は、「未実行」とその理由を記録して先に進む

完了条件: テストと型チェックが通っている、または未実行の理由が記録されている

## 7. レビューでの修正をコミットする
レビューで修正したファイルがあればステージングして1つのコミットにする。コミットメッセージにはレビューで修正した内容を要約する。修正がなければコミットしない。

完了条件: 作業ツリーがクリーンである

## 8. PR本文の材料を集める
実装PRのテンプレートの各節に対応する材料を、次のとおり集める。設計メモは削除済みのため参照せず、PR本文に設計メモの slug やパスを書かない。

| 節 | 材料 |
|---|---|
| 概要 | `main` との差分と、作成・更新した spec から読み取れる変更の目的と結果 |
| 変更内容 | `git log` と `git diff --stat` から読み取れる主な変更(層やモジュール単位で要約) |
| 作成・更新した spec / ADR | `docs/spec` と `docs/adr` 配下の差分ファイルと、それぞれの変更の要約 |
| テスト・型チェックの結果 | 手順6の結果(未実行ならその理由) |
| 見送った指摘 | 手順5で記録した見送った指摘。なければ「なし」 |

完了条件: テンプレートの全ての節の材料が揃っている
