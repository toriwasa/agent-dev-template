設計ワークフローの設計レビュータスクを実行します。タスクの定義・完了条件は `docs/workflow/design-workflow.md` の「設計レビュータスク」節、重大度と承認ゲートは `docs/workflow/README.md` が正本です。最初に両方を読んでください。

## 1. 対象を特定し、事前条件を確認する
- slug は引数があれば引数を使い、なければ現在のブランチ名 `design/<slug>` から求める
- 次のどれかを満たさない場合は、レビューを始めずに理由をユーザーに伝えて終了する
  - 引数がなく、ブランチ名が `design/<slug>` の形式でない
  - `git status --porcelain` が空でない(作業ツリーがクリーンでない)
  - 設計メモ `docs/design-notes/<slug>.md` が存在しない

完了条件: slug と設計メモのパスが決まり、事前条件を全て満たしている

## 2. バリデータを並行して起動する
次の2つのサブエージェントを、1つのメッセージで同時に起動する。

- `design-spec-validator`: 設計メモのパスを渡す
- `coding-standards-validator`: モード「設計」と設計メモのパスを渡す

どちらかがエラー形式で返った場合は、入力を正して起動し直す。

完了条件: 両方のバリデータからレビュー結果を受け取っている

## 3. must を修正する
- 各 must 指摘の根拠(規約・spec)を自分でも確認し、設計メモを修正する
- 根拠を確認した結果、誤検知だと判断した must は修正せず、判断した理由を添えて「判断待ち」に回す
- 修正した場合は手順2の2つのバリデータを再度起動し、新しい must が出ていないことを確認する。再レビューは最大2回とし、2回目でも残った must は「未解決の must」として手順4で提示する

完了条件: 全ての must が「修正済み」「判断待ち」「未解決」のいずれかに分類されている

## 4. 承認ゲートで提示する
次の形式でレポートを提示し、作業を止めてユーザーの判断を待つ。

```md
## 設計レビュー結果
- 設計メモ: docs/design-notes/<slug>.md
- レビュー回数: 2 回(初回 + 再レビュー1回)
- 検証: design-spec-validator(参照 spec: ...)、coding-standards-validator(検証した規約: ...)

## 修正済みの must
- [spec] 変更対象 spec に `csv-export.md` を追加した(一覧の漏れ)

## 未解決の must
なし

## 判断待ち
1. [should][コード規約] ...(architecture.md#logic)
2. [must→判断待ち][spec] ...。誤検知と判断した理由: ...

設計メモを確定する場合は「確定」、修正する場合は番号や修正内容を指示してください
```

- 各項目の先頭に出元のバリデータ(`[spec]` / `[コード規約]`)を付ける
- 判断待ちには通し番号を振り、ユーザーが番号で指示できるようにする

完了条件: レポートを提示し、ユーザーの返答を受け取っている

## 5. ユーザーの指示に対応する
- 修正の指示があれば設計メモを修正し、手順2からやり直す(手順3の再レビュー回数は数え直す)
- 「確定」と返答されたら終了する。設計メモの `status` は `draft` のまま変えず、コミットもしない。`status` の更新とコミットは PR作成タスク(`create-pr`)で行う

完了条件: ユーザーが設計メモを確定している
