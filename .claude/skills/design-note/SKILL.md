設計ワークフローの設計タスクを実行します。タスクの定義・設計メモの必須の節・完了条件は `docs/workflow/design-workflow.md` の「設計タスク」節、slug の規則は `docs/workflow/README.md`、設計メモのフロントマターは `docs/design-notes/README.md` が正本です。最初にこれらを読んでください。

## 1. 入力と slug を決め、事前条件を確認する
- 引数が `docs/investigation/` 配下のパスなら調査メモとして読み込み、slug はそのファイル名から求める。調査メモは gitignore 対象で検索ツールに現れないため、パスを直接読む
- 引数がそれ以外なら依頼内容として扱い、slug は今日の日付と依頼内容の要約から決める。引数がなければ依頼内容をユーザーに尋ねる
- 次のどれかを満たさない場合は、設計を始めずに理由をユーザーに伝えて終了する
  - `git status --porcelain` が空である(作業ツリーがクリーン)
  - `docs/design-notes/<slug>.md` がまだ存在しない
  - ブランチ `design/<slug>` がまだ存在しない

完了条件: 入力と slug が決まり、事前条件を全て満たしている

## 2. ブランチを作成する
`git fetch` で main を最新にし、`origin/main` から `design/<slug>` ブランチを作成して切り替える。

完了条件: `design/<slug>` ブランチにいる

## 3. 設計の前提を集める
- 変更が触れる機能の spec(`docs/spec`)を、`sources` を手がかりに全て読む
- 変更が既存の設計判断に関わる場合は、`status: accepted` の ADR(`docs/adr`)を読む
- `docs/coding-standards/README.md` の索引で適用モードに「設計」を含む規約を読む
- How を書くのに必要なソースコードを読む

完了条件: How と変更対象 spec を書くのに必要な既存の仕様・決定・規約・実装を把握している

## 4. 設計メモを書く
`docs/design-notes/<slug>.md` を `status: draft` で作成し、design-workflow.md の表にある節を全て埋める。

- 調査メモがある場合は、その方針・制約に従う。調査メモの未決事項は、この手順で決めて How に書く
- 書いている途中でユーザーに確認せず、判断が分かれる点は採用した前提と理由を How に、採用しなかった案を Why Not に書く。ユーザーは設計レビューの承認ゲートで設計メモ全体を確定する
- 変更対象 spec には、How によって外から見えるインターフェース・振る舞いが変わる spec を全て挙げ、作成・更新の別と変更内容の要約を書く
- Plan はチェックボックス付きのフェーズで構成し、各フェーズは実装時の1セッションで完了できる粒度にする。各フェーズには完了条件を書く
- Plan には実装フェーズだけを書く。実装後の spec/ADR昇格と PR作成(実装レビューを含む)は、Plan の外で別の SKILL として行う

完了条件: design-workflow.md の表にある全ての節が埋まっている

## 5. コミットする
設計メモだけをステージングしてコミットし、設計メモのパスを報告する。次は `/create-pr` で設計レビューと設計PR作成を行うよう案内する。

完了条件: 設計メモのコミットが作成され、パスを報告している
