実装ワークフローの実装タスクを1フェーズ分実行します。タスクの定義・完了条件は `docs/workflow/implementation-workflow.md` の「セッションの分け方」節と「実装タスク」節、重大度は `docs/workflow/README.md` が正本です。最初に両方を読んでください。

## 1. 対象を特定し、事前条件を確認する
- slug は引数があれば引数を使い、なければ現在のブランチ名 `feat/<slug>` から求める
- `git status --porcelain` が空でない場合は、作業を始めずに理由をユーザーに伝えて終了する
- `git fetch` を実行し、ブランチ `feat/<slug>` があれば切り替え、なければ `origin/main` から作成して切り替える
- 次のどれかを満たさない場合は、実装を始めずに理由をユーザーに伝えて終了する
  - 引数がない場合、ブランチ名が `feat/<slug>` の形式である
  - 設計メモ `docs/design-notes/<slug>.md` が存在し、`status: approved` である(設計PRがマージ済み)
- 設計メモの Plan で未完了のチェックボックスが残っていない場合は、実装せずに終了し、次は `/promote-spec-adr` で spec/ADR昇格を行うよう案内する

完了条件: `feat/<slug>` ブランチにいて、今回実装するフェーズ(Plan で未完了の最初のフェーズ)が決まっている

## 2. フェーズを実装する
- 設計メモ全体を読み、今回のフェーズの内容を実装内容 How に沿ってソースコードとして実装する。後続フェーズの作業には手を付けない
- `docs/coding-standards/README.md` の索引で適用モードに「実装」を含む規約を読み、それに従って書く
- ビジネスロジック関数には単体テストを実装する

完了条件: 今回のフェーズの完了条件を満たすコードとテストが作業ツリーにある

## 3. フェーズの差分をレビューして must を修正する
- `coding-standards-validator` を、モード「実装」、基準 `HEAD` を渡して起動する。基準を `HEAD` にすると、まだコミットしていない今回のフェーズの変更だけが検証対象になる
- エラー形式で返った場合は、入力を正して起動し直す
- 各 must 指摘の根拠となる規約を自分でも確認し、ソースコードを修正する。根拠を確認した結果、誤検知だと判断した must は修正せず、判断した理由を記録する
- 修正した場合はバリデータを再度起動し、新しい must が出ていないことを確認する。再レビューは最大2回とし、2回目でも残った must は「未解決の must」として記録する
- should・nit は修正せず記録する。PR作成タスクで改めてレビューされ、ユーザーが判断する

完了条件: 全ての指摘が「修正済みの must」「誤検知と判断した must」「未解決の must」「should・nit」のいずれかに分類されている

## 4. テストと型チェックを実行する
- `uv run pytest` と `uv run pyright` を実行し、失敗があれば修正する。修正がフェーズの範囲を超える場合は、コミットせずに状況をユーザーに伝えて終了する
- `pyproject.toml` がないなどの理由で実行できない場合は、その理由を記録して先に進む

完了条件: テストと型チェックが通っている、または実行できなかった理由が記録されている

## 5. Plan を更新してコミットする
- 今回のフェーズの完了条件を満たしていることを確認し、設計メモの Plan で当該フェーズのチェックボックスを完了にする
- 実装したファイルと設計メモをステージングしてコミットする。コミットメッセージには今回のフェーズで実装した内容を要約する
- コミット後、次の内容を報告する
  - 実装した内容
  - テストと型チェックの結果(実行できなかった場合はその理由)
  - 修正済みの must
  - 誤検知と判断した must とその理由、未解決の must
  - should・nit の一覧
  - 次の作業: Plan に未完了のフェーズが残っていれば `/implement-phase`、残っていなければ `/promote-spec-adr`

完了条件: Plan の更新を含むコミットが作成され、結果を報告している
