実装ワークフローの実装レビュータスクを実行します。タスクの定義・完了条件は `docs/workflow/implementation-workflow.md` の「実装レビュータスク」節、重大度と承認ゲートは `docs/workflow/README.md` が正本です。最初に両方を読んでください。

## 1. 対象を特定し、事前条件を確認する
- slug は引数があれば引数を使い、なければ現在のブランチ名 `feat/<slug>` から求める
- 次のどれかを満たさない場合は、レビューを始めずに理由をユーザーに伝えて終了する
  - 引数がなく、ブランチ名が `feat/<slug>` の形式でない
  - `git status --porcelain` が空でない(作業ツリーがクリーンでない)
  - 設計メモ `docs/design-notes/<slug>.md` が存在しない
  - 設計メモの Plan で、「実装レビュー」フェーズより前のフェーズに未完了のチェックボックスが残っている

完了条件: slug と設計メモのパスが決まり、事前条件を全て満たしている

## 2. バリデータを起動する
- `coding-standards-validator` を、モード「実装」、基準ブランチ `main` を渡して起動する
- エラー形式で返った場合は、入力を正して起動し直す

完了条件: バリデータからレビュー結果を受け取っている

## 3. must を修正する
- 各 must 指摘の根拠となる規約を自分でも確認し、ソースコードを修正する
- 根拠を確認した結果、誤検知だと判断した must は修正せず、判断した理由を添えて「判断待ち」に回す
- 修正した場合は手順2のバリデータを再度起動し、新しい must が出ていないことを確認する。再レビューは最大2回とし、2回目でも残った must は「未解決の must」として手順4で提示する

完了条件: 全ての must が「修正済み」「判断待ち」「未解決」のいずれかに分類されている

## 4. 承認ゲートで提示する
判断待ち・未解決の must のどちらもない場合は、提示せずに手順6へ進む。ある場合は次の形式でレポートを提示し、作業を止めてユーザーの判断を待つ。

```md
## 実装レビュー結果
- 対象: main との差分(分岐点 <短縮コミットハッシュ>)
- レビュー回数: 2 回(初回 + 再レビュー1回)
- 検証した規約: architecture.md, naming.md, ...

## 修正済みの must
- src/project_name/logic/score.py:12 現在時刻の取得を infrastructure 層に移した(architecture.md#logic)

## 未解決の must
なし

## 判断待ち
1. [should] src/project_name/cli.py:30 ...(naming.md#関数名)
2. [nit] ...
3. [must→判断待ち] ...。誤検知と判断した理由: ...

修正する番号と、必要なら修正方法を指示してください(例: 「1,3 を修正。2 は対応不要」)
```

- 判断待ちには通し番号を振り、ユーザーが番号で指示できるようにする

完了条件: レポートを提示し、ユーザーの返答を受け取っている

## 5. ユーザーの判断を反映する
- 修正を指示された項目を、指示された方法で修正する
- 修正した場合は手順2のバリデータを再度起動し、新しい must が出ていないことを確認する。新しい must が出た場合は手順3と同じ扱いで修正し、再レビューは手順3とは別に最大2回とする。それでも残った must や判断待ちが出た場合は、手順4の形式で再度提示する

完了条件: 判断待ちと未解決の must の全項目について、ユーザーの判断(修正する・しない)が反映されている

## 6. Plan を更新してコミットする
- 設計メモの Plan で「実装レビュー」フェーズのチェックボックスを完了にする
- 修正したファイルと設計メモをステージングしてコミットする。コミットメッセージにはレビューで修正した内容を要約する
- コミット後、修正済みの must と、ユーザーの判断で修正した項目・修正しなかった項目を一覧にして報告する

完了条件: Plan の更新を含むコミットが作成され、結果を報告している
