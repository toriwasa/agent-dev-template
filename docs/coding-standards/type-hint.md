# 型ヒント・データクラスの運用方針

## 型ヒントの運用ルール

- 全ての関数の引数と返り値に型ヒントを定義する
- 変数への直接の型アノテーション（`x: SomeType = ...`）は原則禁止する。ただし空コレクションの初期化（例: `x: list[int] = []`）は許容する
- データ型が不明な変数の型を明示したい場合は `cast()` を使用するが、関数の引数や返り値の型ヒントでの型解決の方が優先される

## データクラスの運用ルール

- 以下のいずれかに該当する場合はデータクラスを定義すること:
  - 関数の引数が5つ以上
  - 引数に `dict[str, dict[...]]` や `list[dict[...]]` など、辞書やリストが2階層以上ネストした構造を渡す場合
  - 関数の返り値が2つ以上（tuple 型での返却は禁止）
- 例外: データクラスインスタンスを生成するファクトリ関数は、フィールド数に応じて引数が5つ以上になることを許容する
- ドメインモデルのデータクラスは `@dataclass(slots=True, frozen=True)` で定義すること
  `slots=True` により `__dict__` を生成しないことで速度向上を図る。
  `frozen=True` によりインスタンス生成後に属性を追加するコードの実装を防止する。
- logic層の関数の引数および返り値の型ヒントに `dict` 型を使うことは禁止する。データクラス型やデータクラス型のイテラブルを使うこと。
  handler 層や infrastructure 層の処理が `dict` 型を利用する場合、データクラスに変換する責務は `dict` 型を利用したファイルが担当する。
- 複数種のデータを扱う場合は Union 型（`TypeA | TypeB`）で表現すること

## Literal 型による分岐

- 条件分岐の判断材料として `str` の値を直接比較するのではなく、`Literal` 型で有効な値の集合を定義し、型レベルで分岐対象を限定すること
- pyright の `reportMatchNotExhaustive` 設定と組み合わせることで、`match` 式での全パターン網羅を保証できる

```python
# NG: 文字列リテラルを直接比較
def process(status: str) -> None:
    if status == "pending":
        ...
    elif status == "completed":
        ...

# OK: Literal 型で有効な値を定義し match で分岐
Status = Literal["pending", "in_progress", "completed"]

def process(status: Status) -> None:
    match status:
        case "pending":
            ...
        case "in_progress":
            ...
        case "completed":
            ...
```

## バリデーション境界

- 外部入力（JSON, API レスポンス等）のバリデーションはパース関数内で完結させ、パース結果の型（dataclass）で構造の正しさを保証すること
- 外部入力文字列パース関数の後続処理では同じフィールドの存在チェックや型チェックを繰り返さないこと

## pyright エラーへの対応方針

`uv run pyright` がエラーを検出した場合、以下の優先順位で対応すること。`# pyright: ignore` によるエラーの抑制は最終手段とし、安易に使用しないこと。

1. **自コードの型付けの問題**: 関数の引数や返り値の型ヒント不足・誤りが原因の場合は、型ヒントを修正すること
2. **サードパーティ製ライブラリの型スタブ不足**: ライブラリ本体には存在するが型スタブ上に定義がない属性・メソッドを利用する場合は、まず該当ライブラリ向けの型スタブパッケージ（例: `pandas` に対する `pandas-stubs`）が存在しないか確認し、存在すれば dev dependency に追加すること。型スタブパッケージの導入で解決できるエラーを `cast` や `# pyright: ignore` で握り潰してはならない
3. **型システムの限界による誤検知**: 型スタブを追加しても解決できず、かつ実行時の型が明らかに正しいとわかっている場合に限り `cast()` を使用すること
4. **上記のいずれでも解決できない場合**: `# pyright: ignore[<ルール名>]` で個別に抑制すること。抑制対象のルール名を必ず明示し、コメントで抑制理由を説明すること

対応後は、抑制範囲を可能な限り狭く保つこと（ファイル全体やモジュール全体の抑制は避け、該当行のみを対象とする）。
