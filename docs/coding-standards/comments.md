# docstring・コードコメントの記載方針
## 関数docstringの記載方針

- 関数のdocstringには、実装の詳細ではなくその関数の目的（何を実現するための関数か）を記載する。
  呼び出し側や後から読む人が、関数名と型ヒントだけでは分からない「この関数が存在する理由・責務の切り分け」を把握できるようにするため。
- 関数内で複雑な処理をしている場合は全体の流れを1行で分かるように概要のみを記載する

## データクラスdocstringの記載方針
- データクラスのdocstringには、フィールド内容の説明ではなくデータクラスの目的（何を実現するためのデータクラスか）を記載する。
  呼び出し側や後から読む人が、フィールド名と型ヒントだけでは分からない「このデータクラスが存在する理由・責務の切り分け」を把握できるようにするため。

## コードコメントの記載方針
- コードのコメントには "何をしているか" ではなく "なぜそうなっているか" （理由・判断根拠）を書く。
  コードを読めば自明な「何をしているか」の重複コメントは避け、理由に集約する
- 局所的な実装について他の実装方針・代替案が存在する場合は "なぜその方針を採用しなかったか"（不採用の理由）も併記する。
  特に、より単純／自明に見える書き方をあえて避けている箇所では必須とする。
  理由を残さないと、後から「なぜこう書かなかったのか」を再検討して手戻りするため。
  複数箇所に影響する代替案についてはコメントではなくADRに記載する
- コードコメントが担当する範囲は、上記の実装局所レベルのWhy Notと、それを補足するHow（複雑な処理の流れ）に限定する。
  仕様レベルのWhy（なぜその仕様になったか）・Why Not（なぜその仕様を採らなかったか）はADRに、What（何を実現しているか）はspecに記載し、コードコメントには複製しない。
  複製すると更新時に片方だけが古くなり、どちらが正しいか判断できなくなるため。
- 仕様の背景に触れる必要がある場合は、内容を書き写さず該当するADRやspecへの参照のみを記載する。
