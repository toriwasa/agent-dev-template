# 設計ワークフロー
調査から設計PR作成までの進め方を定義する。全体の流れ・slug・重大度は [README.md](README.md) を参照

## 1. 調査タスク (`investigate`) (Option)
方針が自明な簡単な実装では省略し、設計タスクから始めてよい。実施するかどうかはユーザーが作業開始時に判断する

- `docs/investigation/<slug>.md` に調査メモを作成する
- 実装内容の方針・制約・代替案などをユーザーと議論した内容を記録する
- 調査メモは gitignore 対象であり、設計メモ作成時にのみ参照される使い捨てのメモとする。最新の仕様を把握する目的で読んではいけない
- 調査タスクと設計タスクは同じローカル環境で連続して行う(worktree や別環境には調査メモが引き継がれない)

### 完了条件
- 調査メモに設計メモ作成に必要な方針・制約・代替案が記録されている

## 2. 設計タスク (`design-note`)
- main から `design/<slug>` ブランチを作成する
- 調査タスクを実施した場合は、調査メモのパスを明示的に受け取って読み込む(検索ツールは gitignore 対象を除外するため、検索で探さない)
- 調査タスクを省略した場合は、ユーザーの依頼内容と既存の spec・ADR・ソースコードを元に設計する
- `docs/design-notes/<slug>.md` に設計メモを `status: draft` で作成する
- 設計メモには次の節を全て含める

| 節 | 内容 |
|---|---|
| 実装背景 Why | なぜこの変更が必要か |
| 実現したい内容 What | 変更によって何が実現されるか |
| 実装内容 How | どのように実装するか |
| 代替案と却下理由 Why Not | 検討した代替案と採用しなかった理由。検討に値する代替案がなければ「ADRなし」と明記する |
| 変更対象 spec | 作成・更新する spec ファイルの一覧と変更内容の要約 |
| フェーズ別作業内容と完了条件 Plan | フェーズごとのチェックボックスと完了条件 |

- Plan の各フェーズは実装時の1セッションで完了できる粒度にする
- Plan には実装フェーズだけを書く。spec/ADR昇格と実装PR作成(実装レビューを含む)は Plan に含めない
- 実装PRは1本とする。実装PRを分けたくなる規模の場合は設計メモ自体を分割する
- 設計メモを書いた後、PR作成タスクと同じ観点で `design-spec-validator` と `coding-standards-validator`(設計レビューモード)を並行して起動してレビューする
- must 指摘はエージェントが修正する。should 以下の指摘は修正せず報告し、PR作成タスクの設計レビューでユーザーが判断する

### 完了条件
- 設計メモの全ての節が埋まっている
- 設計メモの must 指摘が解消されている
- 設計メモをコミットしている

## 3. PR作成タスク (`create-pr`)
レビューを通さずに設計PRを作成しないよう、設計レビューと承認ゲートをこのタスクの中で行う

### 設計レビュー
次のレビューエージェントを並行して起動し、設計メモをレビューする

1. `design-spec-validator` を起動し、変更対象 spec の一覧が実装内容 How と対応しているか(漏れ・過剰がないか)を検証する
2. 同じく `design-spec-validator` で、既存 spec の現在の記述と矛盾する前提で実装しようとしていないかを検証する
3. `coding-standards-validator` を設計レビューモードで起動し、コード規約(アーキテクチャ方針など)に沿った設計になっているかを検証する

- must 指摘はエージェントが修正する
- 修正後、設計メモとレビュー結果(should 以下の指摘を含む)をユーザーに提示し、確定を待つ(承認ゲート)

### 設計PRの作成
- 設計メモの `status` を `approved` に更新してコミットする
- `.github/PULL_REQUEST_TEMPLATE/design.md` に沿って設計PRを作成する。ユーザーが修正しないと判断した指摘は「見送った指摘」に記載する

### 完了条件
- must 指摘が全て解消されている
- ユーザーが設計メモを確定している
- 設計PRが作成されている
